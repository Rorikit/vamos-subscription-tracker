# Перенос Excel в Vamos

Парсер и загрузчик подготовлены для `vamos-subscription-tracker` из каталога `vamos_results`. Загрузка разделена на сохранение источников, проверку записей и запись подтверждённых фактов в продукт. Парсер не запускает приложение, не создаёт демоданные и не использует текущую дату для исторических операций.

## Файлы

- `vamos_importer.py` читает OOXML напрямую, без Excel и дополнительных библиотек. Числа обрабатываются через Decimal. `--stage-db` сохраняет все ячейки, формулы, координаты и кандидатов в отдельной SQLite-базе.
- `aliases.json` содержит варианты из нашего DOCX. Это подсказки для отображения, а не доказательство личности.
- `manifest.example.json` указывает три книги и исходные книги до стандартизации. При совместном чтении сохраняется исходное ФИО до объединения, а неизменность чисел и формул проверяется.
- `apply_reviewed.py` проверяет решения по конкретным строкам и формирует подтверждённые факты. Без `--adapter` выполняется только предварительный просмотр.
- `vamos_adapter.py` записывает подтверждённые оплаты абонементов, посещения и прочие расходы в реальные модели Vamos. Для него нужны зависимости существующего сервера.
- `test_importer.py` и `test_adapter.py` проверяют обработку источников, повторную загрузку, откат, связи и финансовый регистр.

Код также установлен в `server/tools/excel_migration` существующего проекта. Существующие файлы приложения и БД не изменены.

## Предварительный разбор

Из каталога `server` проекта, используя его виртуальное окружение:

```powershell
$env:PYTHONPATH = ".;tools/excel_migration"
.venv/Scripts/python.exe tools/excel_migration/vamos_importer.py --manifest tools/excel_migration/manifest.example.json --aliases tools/excel_migration/aliases.json --out data/excel-review --stage-db data/excel-review/staging.sqlite
```

Перед запуском укажите существующие файлы в manifest. `path` — стандартизированная книга, `original_path` — исходная книга. Оба пути могут быть относительными к manifest. `source_key` остаётся неизменным для одной логической книги: нельзя импортировать исходную и стандартизированную копии как независимые источники.

В каталоге предварительного разбора появятся `summary.json`, `events.jsonl`, `issues.jsonl`, `sheets.jsonl` и `sheet_dates_template.csv`. Полные исходные ячейки сохраняются в staging.sqlite, включая пустые оформленные ячейки. База для предоставленных книг занимает около 0,7 ГБ; это архив источника, а не размер будущей продуктовой базы.

Шаблон дат содержит уникальный ключ `source_key + sheet_index`, отображаемое имя листа, подтверждённую дату ISO и идентификатор площадки. Год и площадку нужно подтвердить. Для применения заполненного шаблона добавьте в manifest:

```json
{"sheet_dates_csv": "sheet_dates_template.csv"}
```

Скопируйте шаблон рядом с manifest. Изменение файлов, кода парсера, дат, привязок людей или словаря меняет отпечаток партии. Для новой версии используйте новую staging-базу: предыдущая не перезаписывается. Повторный запуск неизменной партии не создаёт строк повторно.

Привязка личности задаётся по исходному варианту, в нижнем регистре, с нормализованными пробелами:

```json
{"person_bindings": {"student": {"пример а.": "123"}, "teacher": {"пример преподаватель": "45"}}}
```

Без привязки продуктовый ID отсутствует. Ранее объединённые фамилии не превращаются в один Participant автоматически. Создание справочника людей и исторических абонементов должно опираться на подтверждённые записи, включая начальные остатки и исторические версии тарифов.

## Проверка и запись в продукт

Возьмите `fingerprint` из summary и `record_key`, список issues и координаты платежей из events. Пример решения для оплаты абонемента:

```json
{
  "fingerprint": "ОТПЕЧАТОК_ПРОВЕРЕННОЙ_ПАРТИИ",
  "decisions": [{
    "record_key": "КЛЮЧ_СТРОКИ_ИЗ_EVENTS",
    "action": "receipt",
    "reviewed_issues": ["ВСЕ_КОДЫ_ИЗ_ISSUES_ЭТОЙ_СТРОКИ"],
    "reason": "Дата, ученик, абонемент и отсутствие повторной записи подтверждены",
    "date": "2026-10-07",
    "site_id": "hall-a",
    "person_id": "123",
    "membership_id": "456",
    "category_id": "membership_payment",
    "payment_cells": ["D40"]
  }]
}
```

Список reviewed_issues должен точно совпадать с кодами конкретной строки; пример не является готовым решением. Оплаты берутся только из выбранных валидных денежных ячеек, не из стоимости абонемента, формулы выручки или начисления педагогу. Сумма в решении не редактируется. Для одинаковых настоящих платежей требуется `distinct_payment_confirmations`: список idempotency_keys всей совпавшей группы и причина, почему это разные операции. Без подтверждения возможное дублирование блокируется.

Предварительный просмотр подтверждённых фактов:

```powershell
.venv/Scripts/python.exe tools/excel_migration/apply_reviewed.py --stage-db data/excel-review/staging.sqlite --decisions decisions.json --out approved.jsonl
```

Для посещения используйте `action=attendance`, student_id, teacher_id, session_id, membership_id и revision_id. Историческое событие расписания должно быть подтверждено как completed, с правильной датой, преподавателем и площадкой. Финансовые снимки берутся из указанной исторической MembershipRevision, не из текущего тарифа. Выберите balance_mode:

- `decrement` — списать занятие из предварительно восстановленного остатка; списание атомарное и выполняется один раз.
- `opening_balance_already_accounts_for_visit` — историческое посещение уже учтено в начальном остатке на дату переезда; повторного списания нет.

Для прочего расхода используйте action=expense, category_id существующей категории, title и выбранные payment_cells. Категория и исходный канал сохраняются в журнале миграции; ExtraExpense не имеет соответствующих отдельных полей. Выплаты педагогам не записываются в ExtraExpense, поскольку это может удвоить расходы вместе с начислениями.

Для записи сначала сделайте резервную копию и испытайте ту же партию на копии продуктовой БД. Команда ниже изменяет выбранную БД; она не выполнялась в ходе разработки:

```powershell
$env:VAMOS_IMPORT_DB = "sqlite:///C:/migration-test/vamos-copy.db"
$env:VAMOS_IMPORT_CONFIG = '{"operator_id":1,"sites":{"hall-a":"Марксистская"},"channel_map":{"cash":"cash","bank":"card","qr":"card","yookassa":"card"}}'
.venv/Scripts/python.exe tools/excel_migration/apply_reviewed.py --stage-db data/excel-review/staging.sqlite --decisions decisions.json --out approved.jsonl --adapter vamos_adapter:create_adapter
```

Названия площадок должны совпадать с ScheduleEvent.location. Требуется существующий активный оператор admin. Явное сопоставление каналов обязательно: текущая продуктовая аналитика различает cash/card; исходные QR/ЮKassa сохраняются в provenance. Adapter создаёт только служебную таблицу excel_import_deliveries, не пересоздаёт таблицы приложения. В одной транзакции создаются бизнес-записи, финансовые начисления посещений, аудит и ключи идемпотентности. При ошибке партия откатывается. После записи выполняйте финансовую сверку и проверку остатков в самом Vamos.

## Границы автоматизации

Базовый адаптер не загружает аренду, бар, милонги и зарплатные выплаты под видом Payment: Payment обязательно связан с абонементом, а подходящего общего кассового регистра в проверенной модели нет. Эти источники сохранены в staging и остаются на проверке. Для завершения полного переезда нужны согласованная модель общего денежного регистра либо отдельные адаптеры конкретных бизнес-процессов. Остатки абонементов, возвраты, переносы и отмены нельзя восстановить только по одной колонке «Абонемент».

`UNMAPPED_NUMERIC_CELLS` включает нумерацию строк, итоги и непонятные числовые блоки; это список покрытия для проверки, а не сумма потерянных денег. `INVALID_PAYMENT_VALUE` включает заголовки/формулы, попавшие в финансовую область, и действительно некорректные значения. Ни один такой результат не принимается за реальный платёж.

Все выходные данные содержат персональные и финансовые сведения. Не включайте staging.sqlite, исходные Excel, decisions с ФИО или полные previews в Git. Храните их с теми же правами доступа и резервным копированием, что и продуктовую БД.

Проверка:

```powershell
.venv/Scripts/python.exe -m unittest discover -s tools/excel_migration -p "test_*.py" -v
```
