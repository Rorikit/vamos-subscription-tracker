# Finance Refactor Review

## Найденные проблемы

- Заработок преподавателя считался как полная стоимость занятия, без отдельной ставки преподавателя.
- Старые занятия могли пересчитываться от текущей цены абонемента и текущих настроек.
- Страница «Финансы» смешивала продажи, оплаты и заработок в неочевидные показатели.
- Возвращенные занятия нужно было сохранять в истории, но исключать из финансовых итогов.

## Что изменено

- В `Membership` добавлено поле `teacher_lesson_rate`: фиксированная выплата преподавателю за занятие.
- В `Visit` добавлены поля финансового снимка: `lesson_price`, `teacher_lesson_rate`, `teacher_earning`, `school_earning`.
- При списании занятия финансовый снимок рассчитывается и сохраняется сразу.
- При возврате занятия сохраненные суммы не обнуляются, но `is_cancelled = true` исключает занятие из итогов.
- `/finance/summary` возвращает продажи абонементов, полученные оплаты, стоимость проведенных занятий, выплаты преподавателям, доход школы и средние показатели.
- `/finance/teacher-earnings` возвращает подробную расшифровку по преподавателям и занятиям.
- Страница «Финансы» перестроена под новые показатели и показывает распределение стоимости занятий между преподавателями и школой.

## Миграции

Миграции выполняются при старте backend для локальной SQLite-базы:

- добавляется `teachers.teacher_share_percent`;
- добавляются финансовые поля в `visits`;
- старые посещения получают расчетный финансовый снимок.

## Восстановление старых данных

Для старых посещений финансовый снимок восстановлен расчетным способом:

```text
lesson_price = membership.price / membership.total_lessons
teacher_earning = membership.teacher_lesson_rate
school_earning = lesson_price - teacher_earning
```

Если раньше цена абонемента или ставка менялись, восстановленные значения могут отличаться от фактической исторической ставки. Новые посещения сохраняют точный снимок на момент списания.

## Schedule Review

### Принятые решения

- `ScheduleEvent` отделен от `Visit`: событие отвечает за планирование, а `Visit` создается только при фактическом проведении и списании.
- Участники занятия вынесены в `ScheduleEventParticipant`, чтобы одно событие могло содержать несколько учеников и отдельные статусы посещаемости.
- Проведение занятия выполняется через существующий `write_off_visit`, поэтому остатки абонементов и финансовый снимок остаются единым источником истины.
- Возврат из расписания вызывает существующий `cancel_visit`, а само событие остается исторически проведенным.
- Повторения в MVP создают отдельные события с общим `recurrence_group_id` и JSON `recurrence_rule`; это оставляет путь к RRULE без переписывания данных.
- Конфликт преподавателя проверяется на backend по пересечению `starts_at < existing.ends_at` и `ends_at > existing.starts_at`; отмененные события конфликт не создают.

### Ограничения текущей версии

- В проекте нет Alembic-инфраструктуры, поэтому новые таблицы создаются через существующий startup-паттерн `Base.metadata.create_all`. Для production перед следующим крупным релизом желательно добавить Alembic.
- Drag-and-drop и resize реализованы как безопасный перенос через форму, без отдельной календарной библиотеки.
- Timezone хранится как локальное naive datetime приложения; при мультичасовых поясах нужен отдельный переход на timezone-aware значения.
- RBAC для роли преподавателя пока не введен: расписание доступно ролям `admin` и `operator`.

## Оставшиеся технические долги

- Нет полноценной системы миграций Alembic; для локального MVP используются безопасные startup-миграции SQLite.
- Frontend-тесты пока не добавлены отдельным test runner, проверка UI покрыта TypeScript/Vite build.
- Для production-деплоя желательно заменить локальный bearer-token секрет на управляемый секрет окружения.
